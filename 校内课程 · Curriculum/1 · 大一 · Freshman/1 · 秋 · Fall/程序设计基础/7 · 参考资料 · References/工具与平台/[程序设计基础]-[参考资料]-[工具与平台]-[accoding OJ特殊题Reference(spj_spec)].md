# accoding OJ 特殊题 Reference

本文面向特殊题出题人、验题人与评测维护者，说明 accoding OJ 中 Special Judge（SPJ）的执行模型、可用接口、典型判题结构、资源控制、数据组织与验收方法。本文覆盖实时交互题、通信题、源码检查题，以及利用源码读取接口实现的 Quine、源码风格检查等具体实例。

> 适用范围：本文中的固定路径、运行参数与身份信息来自当前已验证的 accoding 评测环境。评测镜像、运行器或后台实现发生变化后，应重新核验相关路径、参数和行为。

---

## 1. 判题模型总览

### 1.1 普通评测与 SPJ 的执行顺序

一次带 SPJ 的普通评测按以下顺序执行：

1. 编译学生提交。
2. 使用当前测试点的输入文件运行学生程序。
3. 将学生程序在普通运行阶段产生的标准输出保存为输出文件。
4. 启动 SPJ，并向 SPJ 传入当前测试点的输入文件、答案文件和学生输出文件。
5. SPJ 根据题目协议返回当前测试点的得分与结果标签。

SPJ 的入口形式为：

```cpp
int main(int argc, char **argv) {
    // argc == 4
    // argv[0]：SPJ 自身程序名
    // argv[1]：当前测试点输入文件
    // argv[2]：当前测试点答案文件
    // argv[3]：学生程序在普通运行阶段产生的输出文件
}
```

其中，`argv[1]`、`argv[2]`、`argv[3]` 是 SPJ 最基本、最稳定的文件接口。对于普通自定义比较题，只依赖这三个路径即可完成判题；交互题、通信题和源码检查题会进一步使用评测环境中的进程、源码与文件系统接口。

### 1.2 SPJ 的判定输出协议

当前环境中，SPJ 正常判定时向标准输出写两行：

```text
1
Accepted
```

或：

```text
0
Wrong Answer
```

第一行表示当前测试点得分，第二行表示结果标签。SPJ 进程本身通常保持退出码 `0`；仅通过 `return 1` 无法表达上述得分协议。测试点的最终计分还取决于后台为该测试点设置的权重。

SPJ 的标准输出应只用于平台判定结果。交互题中发给学生程序的消息必须写入学生程序标准输入所对应的通道，不能把协议消息写到 SPJ 自身的标准输出，否则会破坏平台结果格式。

检查器自身发生错误时，可以输出 `0` 和专用错误标签，例如：

```text
0
Source Checker Error
```

页面最终如何映射此类标签取决于平台实现，因此排错时应同时检查 SPJ 本地诊断、运行日志和后台实际状态。

### 1.3 编译与普通运行仍然是前置条件

SPJ 并不会取代平台的编译和普通运行阶段。若学生程序编译失败、普通运行超时或异常退出，评测可能在进入 SPJ 前已经结束。因此，交互题和通信题通常需要给普通运行阶段设计一个“预运行”分支，使学生程序收到特殊输入后能够立即正常退出。

源码检查题也受这一限制。即使 SPJ 可以读取原始提交源码，只有成功进入 SPJ 的提交才会执行源码规则检查；如果希望检查无法编译的代码片段，需要另外设计提交入口或评测流程。

## 2. SPJ 可用接口总览

### 2.1 测试点文件接口

SPJ 启动时直接获得三个测试点文件路径：

| 接口 | 路径来源 | 典型用途 |
| --- | --- | --- |
| `argv[1]` | 当前 `.in` 文件 | 公开输入、预运行标记、功能输入 |
| `argv[2]` | 当前 `.ans` 文件 | 标准答案、私有状态、隐藏目标 |
| `argv[3]` | 学生普通运行输出 | 自定义比较、功能输出检查、Quine 字节比较 |

三者的具体含义由题目协议定义。对于交互题和通信题，普通运行常常只是预运行，因此 `argv[3]` 可以完全不参与正式阶段的协议；对于源码风格题，`argv[3]` 可以用于检查学生程序的功能输出；对于 Quine，`argv[3]` 则直接作为源码比较对象。

### 2.2 学生可执行文件接口

当前评测环境中，学生提交编译后的可执行文件位于：

```text
/test/main
```

SPJ 可以在自身执行期间再次启动该程序。交互题与通信题依赖这一能力，在 SPJ 内部主动创建新的学生进程，并为每个阶段构造不同的标准输入。

预运行进程与 SPJ 内再次启动的正式进程是不同进程。每次重新启动都会重新初始化全局变量、静态存储区、栈和堆，因此不能依赖前一次运行的内存状态。

### 2.3 原生运行器接口

当前评测环境提供原生运行器：

```text
/utils/process_monitor
```

交互题和通信题通过该运行器启动 `/test/main`，而不是直接执行学生程序。运行器承担资源限制和以选手身份运行等职责。

已验证的典型参数包括：

```text
-t 1000
-m 65536
-p 5
-uid 8194
-gid 8194
```

其中，`-t`、`-m`、`-p` 分别用于设置时间、内存和进程数量限制；`-uid 8194 -gid 8194` 表示以当前评测环境规定的选手身份运行。这里的 UID/GID 是 Linux 进程身份，与网站用户编号无关。

运行器的完整命令行参数顺序、报告格式和计时口径应以目标评测镜像中的实际实现为准。SPJ 内部通常还需要额外设置墙钟截止时间，以处理阻塞 I/O 或学生进程未正常结束的情况。

### 2.4 SPJ 自身可执行文件路径

平台编译 SPJ 后，当前环境中的可执行文件位置为：

```text
/test/__special_compare__
```

普通出题通常不需要直接访问该路径，但在调试运行环境、检查工作目录和进程关系时可以将其作为定位依据。

### 2.5 数据目录接口

上传的正式测试点文件位于：

```text
/data/data/
```

SPJ 正常应优先使用 `argv[1]`、`argv[2]` 提供的具体文件路径，而不是自行拼接 `/data/data/`。固定数据目录更适合用于环境核验和问题定位。

### 2.6 原始提交源码接口

当前评测环境会保留学生原始提交源码，固定路径为：

```text
/submission/__main__
```

SPJ 可以按字节读取该文件，用于以下功能：

- 源码逐字节比较；
- 源码长度检查；
- 换行、Tab、行尾空格等格式检查；
- 关键字、标识符、禁用函数等词法规则检查；
- 将源码交给额外的解析器或语法工具进行更高层级分析。

源码读取应按二进制字节串处理。若规则涉及 NUL、CRLF、末尾换行或任意字节比较，不能依赖 `strlen` 或传统 C 字符串语义。

### 2.7 提交语言元数据接口

当前评测环境中的语言标记文件为：

```text
/submission/__lang__
```

已核实的值包括：

```text
c
c++
```

读取语言标记时，可以去掉末尾的 `CR`/`LF` 后再比较。迁移到其他语言前，需要重新验证语言标记值、多文件提交行为，以及头文件、附加文件或生成源码是否会被收集到 `/submission`。

### 2.8 文件系统与进程身份接口

当前交互、通信实现使用临时目录和 FIFO 建立 SPJ 与学生程序之间的通信。已验证的做法包括：

- 使用 `mkdtemp` 创建临时目录；
- 临时目录权限设为 `0700`；
- FIFO 权限设为 `0600`；
- 在启动学生进程前准备标准输入、标准输出和标准错误重定向；
- 私有数据读取完毕后关闭对应文件描述符；
- `fork` 后关闭与子进程无关的描述符；
- 运行结束后回收进程并删除临时文件。

学生程序与 SPJ 处于不同的运行身份。学生程序应经 `/utils/process_monitor` 以选手 UID/GID 启动，不能因为 SPJ 自身权限较高而绕过运行器直接执行学生代码。

## 3. 文件读取与输出解析接口

### 3.1 读取输入文件与答案文件

普通文本题可以直接使用 C++ 流读取 `argv[1]` 和 `argv[2]`。如果答案文件承载私有状态，SPJ 应完整验证其格式和范围，避免私有数据损坏后进入未定义分支。

例如：

```cpp
#include <fstream>
#include <string>

std::ifstream fin(argv[1]);
std::ifstream fans(argv[2]);

int n;
if (!(fin >> n)) {
    // checker error
}

std::string secret;
if (!(fans >> secret)) {
    // checker error
}
```

测试数据由出题系统生成并不意味着 SPJ 可以省略格式校验。检查私有数据范围、组数和结构有助于在上传错误数据时快速定位问题。

### 3.2 读取学生普通运行输出

`argv[3]` 指向学生在普通运行阶段产生的输出文件。SPJ 可以按题目需要进行 token 解析、逐行解析或完整字节串比较。

若题目只允许一个整数，应同时检查：

- 是否成功读取整数；
- 是否超出数值范围；
- 后面是否还有额外 token；
- 输出文件是否超过合理字节上限。

若题目要求逐字节相等，应读取完整字节串，并保留空格、Tab、NUL、CR/LF 和文件末尾状态。

### 3.3 有界读取

任何来自学生程序、源码文件或运行日志的读取都应设置明确上限。推荐接口形式：

```cpp
bool read_bounded_file(const std::string &path,
                       std::string &out,
                       std::size_t limit);
```

实现时至少处理：

- 打开失败；
- 文件不是普通文件；
- 文件声明大小超过上限；
- 实际读取累计字节超过上限；
- 中途读取错误；
- NUL 字节；
- 空文件是否允许。

如果使用 `getline` 逐行读取，不能只在读完整行之后再检查累计量，因为单行本身可能非常长。对学生可控内容更适合固定块读取，并在每次读取前后检查累计上限。

### 3.4 安全读取 `/submission`

源码读取可以先打开 `/submission` 目录，再使用 `openat` 打开目标文件。已验证的安全选项包括：

```cpp
O_NOFOLLOW | O_NONBLOCK | O_CLOEXEC
```

随后使用 `fstat` 验证目标是普通文件。这一做法可以拒绝符号链接、目录和 FIFO，避免错误地跟随链接或对管道进行阻塞读取。

逻辑框架如下：

```cpp
int dirfd = open("/submission", O_RDONLY | O_DIRECTORY | O_CLOEXEC);
int fd = openat(dirfd, "__main__",
                O_RDONLY | O_NOFOLLOW | O_NONBLOCK | O_CLOEXEC);

struct stat st;
fstat(fd, &st);
if (!S_ISREG(st.st_mode)) {
    // reject as checker error
}
```

源码长度和实际累计读取字节数都应检查。对于当前已验证实现，源码与输出的读取上限均可设置为 `65536` 字节。

## 4. 子进程启动与双向通信接口

### 4.1 再次启动学生程序

交互题和通信题的核心能力是：SPJ 在自身运行期间再次启动 `/test/main`，并控制该进程的标准输入、标准输出和生命周期。

推荐的抽象接口可以设计为：

```cpp
struct RunResult {
    int monitor_exit_code;
    int program_exit_code;
    bool timed_out;
    std::string stdout_data;
    std::string stderr_data;
};

RunResult run_submission(const std::string &input,
                         int time_limit_ms,
                         int memory_limit_kb,
                         int process_limit);
```

具体实现可基于临时文件、FIFO 或匿名管道。无论采用何种通道，都应由 SPJ 明确负责输入是否完整写入、输出是否完整读取、超时如何中断、子进程如何回收。

### 4.2 FIFO 双向交互

实时交互需要同时保持两条方向相反的通信通道：

```text
SPJ -> 学生标准输入
学生标准输出 -> SPJ
```

原有结构使用两条 FIFO。在正式交互开始后，SPJ 发送公开信息，然后持续读取学生命令并返回回复，直到学生提交最终答案或出现协议错误。

学生程序每次期待即时回复的输出都必须刷新。例如：

```c
printf("? %d %d\n", l, r);
fflush(stdout);
```

只输出换行并不能保证管道环境下立即刷新。

### 4.3 完整写入

对 FIFO、管道或文件描述符执行 `write` 时，不能假设一次调用会写完全部字节。稳健的发送函数应循环处理：

- 部分写入；
- `EINTR`；
- `EAGAIN`；
- 对端提前退出；
- 总体截止时间。

推荐接口：

```cpp
bool write_all_until(int fd,
                     const char *data,
                     std::size_t size,
                     std::chrono::steady_clock::time_point deadline);
```

如果消息较大，还需要将写入事件与读取事件协调，避免双方同时等待造成死锁。

### 4.4 行协议读取

对于命令式交互，SPJ 可以逐字节或分块读取，直到遇到换行。解析器应明确规定：

- 单行最大长度；
- 是否接受空行；
- 是否允许 NUL；
- token 数量；
- 数值格式；
- 是否允许前导零、正号、小数写法；
- 最终答案后是否允许额外输出。

原实时交互模板的单行限制为最多 `127` 个非换行字节，并拒绝 NUL。扩展协议时需要同步修改这一限制。

### 4.5 运行结果检查

学生程序给出正确答案后，SPJ 仍应等待并检查进程结束状态。一个正式阶段只有同时满足下列条件才应判定成功：

- 题目答案正确；
- 所有协议消息合法；
- 运行器进程正常结束；
- 运行报告中的结果码为成功；
- 学生程序退出码为 `0`；
- 没有禁止的尾随输出；
- 没有超时或异常退出。

在收到正确答案后立即返回 AC，会遗漏“答对后崩溃”“答对后持续运行”“答对后继续输出”等错误情况。

## 5. 资源控制与隔离

### 5.1 时间限制

后台普通运行限时不会自动同步到 SPJ 内部再次启动学生程序时使用的限制。交互题与通信题至少存在两层时间控制：

1. `/utils/process_monitor` 对单次学生进程施加的运行限制；
2. SPJ 自身用于控制整体等待的墙钟截止时间。

已验证的交互模板中，正式交互的整体墙钟截止时间为约 `3` 秒，收尾等待最多约 `1500 ms`。已验证的通信模板中，每次启动的等待预算约为 `1000 + 1000 ms`，每次收尾最多约 `500 ms`，两个角色合计另设约 `4000 ms` 的组级预算。

这些常量不能直接视为覆盖所有路径的严格总时限。输入写入、进程创建、日志收集和清理都可能引入额外开销，因此正式题应在目标平台按最大组数和最大消息量进行压力验证。

### 5.2 内存与进程限制

交互和通信题的典型再启动参数为：

```text
-m 65536
-p 5
```

分别表示内存限制和进程数限制。修改后台内存设置不会自动修改 SPJ 中硬编码的运行器参数，因此两处需要同步维护。

### 5.3 输出量限制

不能只限制单行长度。学生程序可以输出大量短行，因此应分别对以下内容设置累计上限：

- 学生标准输出；
- 学生标准错误；
- SPJ 自己保存的日志或运行报告；
- 单条协议消息长度；
- 整个阶段的消息总量。

### 5.4 通信隔离

重新启动进程只能清空该进程原有的内存状态，不能自动隔离文件系统、环境变量、其他进程或外部资源。通信题中两个角色使用同一个 Linux UID；如果存在共享可写文件，就可能形成题面规定信道以外的通信渠道。

如果题目要求“只能通过指定载体通信”，应额外验证：

- 两个角色是否使用独立工作目录；
- 是否存在双方均可写的持久文件；
- 是否存在可继承文件描述符；
- 环境变量是否携带跨阶段状态；
- 是否允许创建后台进程；
- 每提交容器是否真正隔离；
- UID/GID、附加组、capabilities 和系统调用限制是否符合预期。

此类隔离属于执行环境性质，不能仅通过题面或源码检查保证。

## 6. 特殊题结构

### 6.1 实时交互题

实时交互题的典型流程为：

```text
OJ 编译学生程序
  -> 普通运行：输入预运行标记，程序立即退出
  -> 调用 SPJ
  -> SPJ 读取私有状态
  -> SPJ 建立双向通信通道
  -> SPJ 经运行器再次启动 /test/main
  -> SPJ 发送公开初始信息
  -> 学生询问
  -> SPJ 校验询问并回复
  -> 重复若干轮
  -> 学生提交最终答案
  -> SPJ 检查答案、额外输出、退出状态与运行报告
  -> 输出测试点判定
```

题面必须完整定义：初始输入、命令格式、参数范围、询问次数、异常通知、EOF 处理、最终答案格式、最终答案后是否允许输出、下标起点和刷新要求。

### 6.2 通信题

通信题使用同一份学生程序扮演多个角色。SPJ 负责在不同阶段启动不同进程，并控制每个角色可见的信息。

典型流程为：

```text
普通运行：op = 0
  -> SPJ 内部预运行：op = 0
  -> 对每组私有数据：
       启动角色 A
       解析 A 的输出
       SPJ 修改受限载体
       根据修改后的载体构造角色 B 输入
       启动角色 B
       比较 B 的答案与隐藏目标
  -> 所有组通过后返回 Accepted
```

如果每个测试点有 `q` 组私有数据，且每组包含两个正式角色，那么 SPJ 内部会启动 `1 + 2q` 次学生程序；连同平台外层普通运行，总启动次数为 `2 + 2q`。

角色之间允许传递的内容必须由 SPJ 实际构造。不能把角色 A 声称“已经修改一次”直接当成事实，也不能提前在 `.ans` 中写死角色 B 的输入。若题目限制消息长度或修改次数，应由 SPJ 根据真实输出和真实载体变化进行检查。

### 6.3 源码检查题

源码检查题的核心流程为：

```text
普通编译与运行成功
  -> SPJ 读取 /submission/__lang__
  -> SPJ 读取 /submission/__main__
  -> 验证语言、文件类型和长度
  -> 执行源码规则
  -> 按题意读取 argv[3] 检查功能输出
  -> 汇总源码规则和功能规则
  -> 返回测试点判定
```

源码规则可以分为四个层级：

| 层级 | 适合检查的规则 | 需要明确的边界 |
| --- | --- | --- |
| 原始字节扫描 | LF/CRLF、真实 Tab、行尾空格、文件末尾换行 | 注释和字符串是否同样受限 |
| 词法分析 | 关键字、注释、标识符、禁用函数名 | 字符串、转义、注释、预处理续行 |
| Token/语法分析 | 缩进层级、括号布局、声明结构、函数签名 | 宏、标签、多行表达式、初始化列表 |
| AST/语义分析 | 递归、变量类型、调用关系、重载 | 宏展开、作用域、函数指针等 |

若检查 `goto`，直接字符串搜索会误伤注释、字符串和 `goto_count` 等标识符。此类规则至少需要词法级 token 识别。若需要检查实际调用关系或函数语义，则应使用语法或 AST 级工具，并固定工具版本和参数。

### 6.4 普通自定义比较题

如果题目只需要自定义输出比较，不需要重启学生程序或读取源码，SPJ 只使用 `argv[1..3]` 即可。实现时应明确输出 token 规则、数值误差、额外输出、文件大小上限以及 checker error 与 Wrong Answer 的区分。

这种结构是所有特殊题中最简单的一类，也适合作为调试 SPJ 结果协议和后台配置的最小工程。

## 7. 功能接口实例

本节给出各类接口的具体使用方式。实例用于说明功能如何组合，接口本身的定义以前述章节为准。

### 7.1 实例：区间询问实时交互

设题目隐藏 `1..n` 的一个排列，学生可以询问区间内第二大元素的位置，最终回答全局最大值位置。协议可以设计为：

| 方向 | 消息 | 约束 |
| --- | --- | --- |
| 普通运行输入 | `0` | 学生程序立即正常结束 |
| 正式初始输入 | `n` | 隐藏排列只保存在 SPJ 中 |
| 学生询问 | `? l r` | `1 <= l < r <= n`，限制询问次数 |
| SPJ 回复 | 一个下标 | 区间第二大元素位置 |
| 学生最终答案 | `! p` | `p` 为全局最大值位置 |
| 异常通知 | `-1` 或 EOF | 学生程序应停止并退出 |

学生侧发送询问：

```c
#include <stdio.h>
#include <stdlib.h>

int ask(int l, int r) {
    int reply;
    printf("? %d %d\n", l, r);
    fflush(stdout);
    if (scanf("%d", &reply) != 1 || reply == -1) {
        exit(0);
    }
    return reply;
}
```

SPJ 侧应分别处理：询问格式、参数范围、询问次数、回复计算、最终答案、最终答案后的额外输出、学生进程退出状态和整体墙钟超时。

### 7.2 实例：两阶段棋盘通信

设棋盘为 `8 x 8` 二进制格子。发送者知道棋盘和隐藏目标，只允许翻转一枚硬币；接收者只能看到翻转后的棋盘，需要恢复目标位置。

角色协议：

| 模式 | 学生输入 | 学生输出 |
| --- | --- | --- |
| `op = 0` | `0` | 无输出并立即退出 |
| `op = 1` | 棋盘 + 目标坐标 | 一个翻转坐标 |
| `op = 2` | 翻转后的棋盘 | 目标坐标 |

发送者输出的坐标不会作为额外信息传给接收者。SPJ 解析发送者的输出后，应亲自执行：

```cpp
next[index] ^= 1;
```

随后根据修改后的 `next` 构造接收者输入。

一个可行算法是给格子编号 `0..63`。令 `s` 为所有值为 `1` 的格子编号异或和，目标编号为 `k`；发送者翻转编号 `s ^ k` 的格子，翻转后异或和变为 `k`，接收者重新计算异或和即可恢复目标。

对应 C 程序：

```c
#include <stdio.h>

int main() {
    int op;
    if (scanf("%d", &op) != 1 || op == 0) return 0;
    if (op != 1 && op != 2) return 0;

    int code = 0;
    for (int i = 0; i < 64; i++) {
        int coin;
        if (scanf("%d", &coin) != 1) return 0;
        if (coin == 1) code ^= i;
    }

    if (op == 1) {
        int r, c;
        if (scanf("%d%d", &r, &c) != 2) return 0;
        code ^= (r - 1) * 8 + c - 1;
    }

    printf("%d %d\n", code / 8 + 1, code % 8 + 1);
    return 0;
}
```

这里用到的核心 SPJ 功能包括：重复启动 `/test/main`、为不同角色构造不同输入、解析角色输出、由 SPJ 修改中间载体，以及检查不同阶段的退出状态。

### 7.3 实例：Quine

Quine 题利用“读取学生原始源码”和“读取普通运行输出”两个接口完成判定。

流程为：

```text
编译、普通运行成功
  -> 读取 /submission/__main__ 为 source
  -> 读取 argv[3] 为 output
  -> source 非空
  -> source == output
```

比较必须按完整字节串进行。以下内容都会影响结果：

- 空格；
- Tab；
- 注释；
- NUL；
- 文件末尾是否有换行；
- LF 与 CRLF。

因此应使用 `std::string` 或等价的二进制缓冲区保存长度，不能用 `strlen` 判断源码长度，也不能用 `strcmp` 完成带 NUL 的比较。

Quine 只验证“程序输出与源码字节一致”。如果题面还要求程序不得从外部文件读取自身源码，这属于运行环境限制或行为审查，需要额外机制才能自动约束。

### 7.4 实例：源码风格检查

设题目要求学生用 C 读取两个整数并输出和，同时满足以下源码规则：

| 规则 | 精确定义 |
| --- | --- |
| 文件长度 | `1..65536` 字节 |
| 换行 | 只接受 LF，出现任何 CR 均拒绝 |
| Tab | 整份源文件禁止真实 Tab 字节 |
| 行尾空格 | 每个 LF 前不得紧邻 ASCII 空格 |
| 行长度 | 每行最多 120 字节，不计 LF |
| 文件结尾 | 最后一个字节必须为 LF |
| NUL | 源文件不允许 NUL |

SPJ 可以先调用：

```cpp
check_style(source)
```

并记录首个违规位置。随后读取标准答案和 `argv[3]`，检查功能输出是否正确、是否存在额外字段。

这种题将两个独立功能组合在一起：源码接口负责静态规则，`argv[3]` 负责运行结果。若只想检查风格，也仍然要考虑平台会先进行编译和普通运行。

## 8. 后台配置与数据组织

### 8.1 推荐工程结构

```text
problem/
  problem.md
  solution.md
  answer.c
  compare.cpp
  data/
    01.in
    01.ans
    02.in
    02.ans
  generate_data.py
  verify.py
  verification.json
```

其中：

- `problem.md`：题面与完整协议；
- `solution.md`：算法说明；
- `answer.c`：至少一份可提交参考程序；
- `compare.cpp`：最终 SPJ；
- `data/`：正式测试点；
- `generate_data.py`：可重复生成正式数据；
- `verify.py`：本地协议与判题验证；
- `verification.json`：记录版本、哈希和测试结果。

SPJ 与数据生成器共同定义私有数据格式。修改字段、组数、消息格式或范围后，应同步修改题面、参考程序、反例程序和验证脚本。

### 8.2 后台操作顺序

1. 新建题目，填写题面、允许语言、普通运行时间和内存限制。
2. 在高级设置中启用 SPJ，SPJ 语言使用 C++14，并粘贴完整源码。
3. 成对上传 `.in` 与 `.ans`。
4. 核对测试点文件名、数量、权重和非空状态。
5. 保存后重新进入编辑页，读回题面、SPJ 和关键配置。
6. 先提交参考程序验证一个测试点，再提交针对性错误程序。
7. 上传全部正式数据，覆盖每一种允许语言。
8. 下载线上数据回查文件名、字节数和内容哈希。

后台 SPJ 代码框需要完整源文件。单独上传本地工程中的 `makefile` 不会自动启动交互服务。

### 8.3 测试点文件要求

正式 `.in` 和 `.ans` 都必须非空。没有有效公开输入时，可以使用单个 LF；SPJ 明确忽略答案文件时，可以使用：

```text
unused
```

作为非空占位。

推荐在上传前执行：

```python
from pathlib import Path

root = Path("data")
inputs = sorted(root.glob("*.in"))

assert 1 <= len(inputs) <= 8
assert {p.stem for p in inputs} == {
    p.stem for p in root.glob("*.ans")
}

for inp in inputs:
    for p in (inp, inp.with_suffix(".ans")):
        raw = p.read_bytes()
        assert len(raw) > 0, f"零字节文件：{p}"
        assert b"\r" not in raw, f"含 CR 字节：{p}"
```

一个测试点文件内部的 `q` 或 `T` 只增加单点运行成本，不会变成多个后台测试点。若 SPJ 对组数有硬编码上限，数据生成器也必须遵守该上限。

## 9. 验证方法

### 9.1 分层验证

| 层次 | 验证内容 | 目标 |
| --- | --- | --- |
| 算法验证 | 独立答案、小规模枚举、数学证明 | 参考算法和判定公式一致 |
| 协议验证 | 双向管道、角色重启、格式反例 | 消息流和状态转换正确 |
| SPJ 单元验证 | 直接调用解析器、源码读取器 | 边界和错误分支符合约定 |
| 真实 OJ 验证 | 每种语言的正例与反例 | 编译、路径、运行器、得分协议兼容 |
| 隔离验证 | 状态、权限、文件和进程边界 | 题面规定的通信信道确实成立 |

本地替代运行器只能验证通信逻辑，不能证明真实 `/utils/process_monitor` 的权限、计时和隔离行为。路径、UID/GID、运行报告等平台性质必须通过真实 OJ 验证。

### 9.2 实时交互题的最小反例集

至少覆盖：

- 最小规模和最大规模；
- 合法的零询问答案，如果题目允许；
- 多轮自适应询问；
- 参数越界；
- 空命令；
- 多余字段；
- 超过询问次数；
- 不刷新输出；
- 缺失最终答案；
- 最终答案后继续输出；
- 答对后非零退出；
- 答对后持续运行；
- 最终答案没有换行。

### 9.3 通信题的最小反例集

至少覆盖：

- 不同合法载体状态；
- 所有目标位置；
- 边界消息长度；
- 发送者坐标越界；
- 发送者额外字段；
- 发送者缺失输出；
- 接收者错答；
- 接收者答对后非零退出；
- 单阶段超时；
- 空载体；
- 错误依赖跨阶段内存；
- 非法跨阶段共享状态。

### 9.4 源码检查题的最小反例集

每条源码规则至少准备：

- 一个恰好位于边界上的合法例；
- 一个只违反该规则的最小违规例；
- 一个容易被错误实现误判的合法例；
- 规则组合违规例；
- 源码缺失；
- 符号链接；
- FIFO；
- 语言标记不符；
- 输出错误；
- 答案文件损坏。

源码层的任意字节测试可以直接调用比较器。包含 NUL、全换行等测试串不一定能作为合法 C 程序编译，因此应区分“源码读取单元测试”和“真实提交测试”。

## 10. 常见问题定位

| 现象 | 优先检查 | 处理方向 |
| --- | --- | --- |
| SPJ 尚未执行就 TLE | 学生是否正确处理预运行标记 | 让预运行分支立即正常退出 |
| 交互读不到回复 | 是否换行、是否 `fflush`、是否遇到 EOF | 修正消息格式，检查 SPJ 写入结果 |
| 非法询问后直接 EOF | 错误通知是否真正送达 | 学生同时处理 EOF 与错误码 |
| 答案正确仍 WA | 退出码、运行器报告、尾随输出 | 清理调试输出并正常结束 |
| 通信接收者总是错 | 是否根据本轮发送者输出真实修改载体 | 记录两阶段输入输出逐项核对 |
| 跨阶段全局变量丢失 | 两个角色是否分别启动 | 将允许传递的信息编码到题目载体 |
| `01 2` 被拒绝 | 输出 parser 的整数语法 | 统一题面和解析器规则 |
| Quine 肉眼相同仍 WA | 行尾空格、Tab、CRLF、末尾 LF | 按二进制查首个不同字节 |
| 源码检查器错误 | `/submission`、`__main__`、`__lang__` | 检查路径、语言和文件类型 |
| 风格检查通过仍 WA | 功能输出和额外字段 | 分离验证源码规则与功能规则 |
| 修改后台限时后仍按旧值超时 | SPJ 内部运行器参数 | 同步修改 SPJ 常量并回归 |
| 大量输出导致 SPJ 资源增长 | 是否只限制单行 | 增加 stdout/stderr 累计上限 |
| 增加诊断后页面显示异常 | SPJ 标准输出格式 | 标准输出只保留固定判定协议 |
| 更换数据后结果无变化 | 是否仍引用旧测试点 | 下载当前数据核对文件名与哈希 |

定位两个文件首个字节差异时，可以使用：

```python
from pathlib import Path

source = Path("answer.c").read_bytes()
output = Path("program.out").read_bytes()

for i in range(max(len(source), len(output))):
    if source[i:i + 1] != output[i:i + 1]:
        print("首个差异的字节偏移：", i)
        print("源码：", repr(source[max(0, i - 10):i + 11]))
        print("输出：", repr(output[max(0, i - 10):i + 11]))
        break
else:
    print("逐字节一致")
```

## 11. 上线验收清单

| 项目 | 完成条件 |
| --- | --- |
| 题面 | 协议、可见信息、所有范围、退出方式与限制完整 |
| 数据 | `.in/.ans` 成对、全部非空、私有格式合法、测试点数量符合要求 |
| SPJ | 题意与解析一致，超限和异常路径有明确判定 |
| 运行 | 原生运行器路径与身份验证通过，时间和输出量有界 |
| 源码规则 | 每条规则有精确定义、合法例与违规例，读取失败可定位 |
| 正反例 | 每种开放语言的参考程序通过，典型错误程序被拒绝 |
| 版本 | 线上 SPJ、下载数据与本地最终版本一致 |
| 交付 | 题面、题解、参考程序、数据、SPJ、验证记录和复现命令齐全 |

每次修改后，应按影响范围重新验证。变更文件协议、运行器参数、固定路径、源码读取方式或角色隔离策略时，应重新执行真实 OJ 验证。
