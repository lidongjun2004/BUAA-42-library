<h2 id="1.1">二进制文件输入输出问题</h2>
在最新一期（第五期）作业中，有一道题要求同学们对文件进行读入并且根据读入的字符构建Huffman树，最后将源文件压缩；这里就出现了一般的文本读写模式与二进制读写模式的区别。

文本读写模式即一般情况下我们使用的文本读写模式，如以下程序：

```c
fin = fopen("in.txt", "r");
fout = fopen("out.txt", "w");
```

其中的指定打开模式的字符串"r"和"w"使用的就是默认的文本读写模式。

在这种模式下，程序会认为打开/写入的文件中全部由**可打印字符**构成，并且会自动地根据操作系统的定义对换行符进行转换（读入换行符时自动转化为\n，写入\n时自动转换为对应换行符）；此外，在这种模式下，一些不可打印字符在特定的操作系统下会被认为具有特殊意义，如字符^Z（ASCII码为26）在Windows系统下代表文件结束。更为详细的叙述可以参考本网页 [维基百科_C0&C1 Control Code](https://en.wikipedia.org/wiki/C0_and_C1_control_codes).

但是，如果我们要写一份压缩软件的话，压缩前的文件与压缩后再解压的文件显然应该**完全一样**，这就要求我们将文件视为*比特流*来进行读入和输出以完全忽略文件的内容，而不是将文件视为文本。这就需要我们在指定模式的字符串后面加上字符'b'，表示以二进制(binary)的方式进行读入。具体代码如下：

```c
fin = fopen("in.txt", "rb");
fout = fopen("out.txt", "wb");
```

此外，如果你的程序没有使用二进制读入方式但也通过了评测，这应该是因为Linux系统中的文本读入模式不会对文本进行太多的多余处理；并且不使用二进制读入进而出现错误的情况一般仅出现在解压缩的过程中，所以说在做实验题时你可以不用在意这一点。

<h2 id="1.2">if、if-else 与 switch</h2>
一种经典的对输入的指令/操作码（op code）的处理方式是使用switch结构。伪代码如下：

```c
while(some_condition) {
  c = getchar();
  switch (c) {
    case '1':
      do_something();
      break;
    case '2':
      do_something_else();
      break;
    ...
    default:
      puts("error!!!\n");
  }
}
```

与这种结构对等的一种结构是if-else结构：

```c
while(some_condition) {
  c = getchar();
  if (c == '1') {
    do_something();
  } else if (c == '2') {
    do_something_else();
  } else {
    puts("error!!!");
  }
}
```

但是注意，该结构中的else**不可以被去掉**：这是因为在do_something()中，作为判断依据的c可能会被修改，导致在一次循环中程序执行了**多个if块**中的内容，最终导致程序结果出错。本错误在第四次作业的第四题中大量出现。

同时也提醒各位同学在编程的过程中时刻保证自己写出的代码与自己所设想的处理过程完全吻合，在确认不会出问题的前提下再适当精简结构，不要顾此失彼。

<h2 id="1.3">函数返回问题与Warning的修复</h2>

众所周知，一个函数应当有一个返回值，除非这个函数被定义为void类型；

但是，经常有同学将代码写成如下结构：

```c
int function(){
  while() {
    do_something();
    if(some_condition) {
      return some_integer;
    }
  }
  // no expected return statement
}
```

由于题目中的约束保证了while循环中一定会return，因此有的同学就省略了函数最后的return，认为就算写了return也不会执行；

但是，由于这违反了这个函数一定会返回一个值的约定，这可能会让编译器在优化该程序时发生不可预知的错误，从而导致运行时出现奇怪的问题。

因此，请严格遵循编程的规范，并且**消除所有不能确定后果的Warning**，保持良好的码风来提高正确率。

在消除Warning这一方面，如果不能确定其报错原因，你或许可以选择直接将Warning信息粘贴到百度搜索栏中并搜索，进而找到修复此Warning的方法（绝大多数情况下都能够找到）；此外，如果只是个别单词/术语不认识，我们完全可以通过百度来解决这些问题；在遇到疑难杂症时也随时可以截图发到群里进行交流。

最后，请不要因为看不懂Warning或Error的信息就选择逃避该报错，要知道编译器很多时候能够在静态分析的基础上防止程序员写出需要花费数小时来找到并修复的bug。
